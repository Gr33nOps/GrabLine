# GrabLine 1.32.14

Firefox download takeover now happens before a browser download item is created. When GrabLine accepts an ordinary HTTP attachment or binary-file response, including torrent files and archives, Firefox cancels that response at the headers stage instead of starting and pausing a second download. Redirects and duplicate requests are handled without creating duplicate GrabLine jobs.

Update **both the desktop app and GrabLine Connect to 1.32.14**. The Firefox fix is in the extension; updating only the desktop app will not change browser takeover. The Firefox extension now requests `webRequestBlocking` so it can make this decision before the browser starts saving the file. The Chrome package also includes the improved handoff deduplication and retry handling.

Waiting downloads assigned to a named queue now show **Queued: Movies**, for example, in both the list and the detail drawer. Downloads outside named queues retain **Waiting to start**. The status column measures the displayed font so ordinary labels fit; long queue names shorten with an ellipsis and show their full text in a tooltip. Queue names update immediately after a move or rename. The new label is translated in every shipped language.

If GrabLine is closed or rejects a handoff, the original browser download proceeds normally. Browser-generated blobs, POST exports, assistant-generated files and sites requiring a browser verification session remain browser-owned. Once Firefox hands a file to GrabLine, transfer failures and retries stay in GrabLine. Chromium's existing paused-browser fallback remains in place.

Verified with real Firefox direct and redirected file downloads: accepted handoffs created no browser download entries, and a closed-app control completed normally in the browser. Regression coverage includes Firefox response interception, concurrent Chromium handoffs, queue status layout, queue moves and renames, and browser-specific extension packaging.
