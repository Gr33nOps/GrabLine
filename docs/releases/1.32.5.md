# GrabLine 1.32.5

Fixed a connection-release delay near the end of segmented downloads. When a
free worker took over a slow segment's tail, the original worker could finish
its newly shortened range but wait for another chunk from the old response.
It now closes that response immediately after writing its assigned bytes,
allowing the worker to take more work and avoiding unnecessary completion waits.

Improved compatibility with file hosts that reject Range probes: after HTTP
400, 403, 405, 412, 428, or 501, metadata detection retries once with an ordinary
GET. If accepted, the download uses a single full stream. The probe does not
consume the whole file; authentication failures still fail after the bounded
retry. Existing resume and checksum behavior remain covered by regression tests.

The web-page error now explains how to hand off an ordinary file download from
the browser, rather than offering only video-player instructions.

## Verify

- Download a large resumable file and check that the final segments finish
  without waiting for unused response data; compare its published checksum.
- Try a server that rejects ranges: it should download normally using one
  connection instead of failing at metadata detection.
- For download landing pages, use the website's final download button with
  GrabLine browser interception enabled. Pasting the landing page is not the
  same as providing a direct file URL.

The supplied ROMsFun landing page was identified as a timed download page.
Its final browser handoff could not be tested because the browser tool's
site-safety policy blocked access. These changes do not claim to bypass website
challenges or guarantee that specific site's final download. Some speed decline
is normal as fewer bytes remain; disk flushing and server limits still apply.
